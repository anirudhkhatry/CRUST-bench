# Additional datasets: good-vs-bad migration benchmarks — design

**Date:** 2026-09-14
**Status:** design proposed · pilot not yet run
**Working dir:** `relational_mutation_testing_baseline/additional_datasets/`
**Companion:** `relational_mutation_testing_baseline/docs/2026-09-14-bore-benchmarks.md`
(the benchmark/experiment brief this design implements)

---

## 1. The question, and why the existing evidence does not yet answer it

The pipeline's claim is that a test forced to kill a mutant is a better correctness check
than a test an LLM writes when simply asked. Today that claim rests on two numbers that
point in opposite directions:

| measurement | result | what it is scored on |
|---|---|---|
| `full100` funnel kill rate | **97%** | `M'`, a fault *this pipeline ported* into the reference |
| independent-implementation recall ([2026-09-08](../../../relational_mutation_testing_baseline/docs/2026-09-08-mutation-tests-vs-independent-implementations.md)) | **0.23**, and **0.00** on the clean 36-project subset | codex implementations the pipeline never saw |
| PyMigBench `expA` validation | recall 50%, **precision 23%**, FRR 20% | 51 labelled LLM migrations |

The gap between 97% and 0.23 is the whole problem. A mutant the pipeline itself
constructed is not independent evidence, and the one time the tests met code written by
someone else they found almost nothing. The honest reading is that we have measured
*mutant-killing* thoroughly and *fault-detection on foreign code* barely at all — on 51
labelled candidates yielding three true positives.

This design adds two benchmarks whose entire purpose is to close that gap: populations of
**compiling, independently produced GOOD and BAD transformations**, large enough and
balanced enough to compare the mutation-guided arm against the naive LLM arm with the
confusion matrix the brief specifies in §12.

The research question, restated for these benchmarks:

> Given a trusted pre-change program P0 and a migration spec M, do tests generated under
> mutation pressure reject behaviourally-incorrect-but-compiling migrations at a higher
> rate than tests generated by prompting alone, **at the same rate of accepting correct
> ones**?

## 2. The structural insight: Stage 3 disappears

Both benchmarks here are **same-language, behaviour-preserving** transformations — Java 8
to Java 17, and JavaScript module decomposition. This is not a detail; it changes the
instrument.

In C→Rust the test must be re-expressed in another language, and that translation is where
the signal is lost: `F2_transpile_no_compile`, `F3_unsound_on_correct_rust`,
`F4_not_discriminating` are all translation failures, and 305 of 853 transpiled tests
(36%) did not compile against a second implementation at all. None of that exists here.
The migration contract states that the observable surface is preserved, so a test written
against P0 compiles and runs **unchanged** against every candidate.

Three consequences:

1. **The comparison becomes clean.** Every arm emits a suite in one language, frozen once,
   run on identical candidates. ARM M and ARM N then differ in exactly one variable —
   whether a mutant forced the test to prove it discriminates. That is the claim, isolated.
2. **A failure is attributable.** When a test misses a BAD candidate here, it is a weak
   test. In C→Rust it might have been a weak test, a lossy transpilation, or a fault with
   no Rust counterpart, and the funnel needs five outcome codes to tell those apart.
3. **The pipeline is no longer relational.** These benchmarks exercise mutation-guided
   regression test generation, which is what the brief's §10 and §11 actually describe.
   The relational C↔Rust result stands on its own; this is the generalisation experiment.

```
                    P0  +  migration spec M
                            |
   +----------------+-------+--------+------------------+
   | ARM M          | ARM N          | ARM A            | ARM C
   | mutation-guided| naive LLM      | developer tests  | ceiling
   | P0 -> P0',     | "here is P0    | the repo's own   | sees the
   | T passes P0    |  and M, write  | suite            | GOOD->BAD
   | and fails P0'  |  tests"        |                  | diff
   | (executed gate)|                |                  |
   +----------------+----------------+------------------+
                            |   <-- FROZEN + HASHED HERE
                            v
        GOOD_1..n (verified preserving)   BAD_1..n (compiles, subtly wrong)
```

ARM A is the brief's Baseline A, ARM N its Baseline B, ARM C the analogue of
`baseline_rustnative.py` — it sees the GOOD→BAD diff, so it is an upper bound rather than
a technique, and `1 - ARM C's rejection rate` is the floor under every other arm's miss
rate. Baseline C (a generic automated generator such as EvoSuite) is **out of scope for
the pilot** and noted in §11 as future work.

### ARM N is a matched control, not a single draw

**Decision, 2026-09-15 (user-directed).** A whole-branch review found that ARM M received
roughly 6.75x ARM N's generation budget *and* best-of-6 selection: it proposes up to 6
faults, writes a test for each with its own repair budget, and keeps only those that both
compile and kill. ARM N got one suite, one repair budget, no selection. If ARM M won under
that arrangement, the result could not distinguish "mutation pressure works" from
"six filtered samples beat one unfiltered sample".

ARM N is therefore a **matched control**:

| | ARM M | ARM N (matched) |
|---|---|---|
| draws | 6 | 6 |
| per-draw budget | `_generate_with_repair`, build-errors-only | identical |
| filter | green on P0 **and red on the mutant** | green on P0 |
| assembly | concatenate, validate composite, drop colliding | identical |

The single surviving difference is the kill gate, which is the variable under test.

Two residual asymmetries are intrinsic and are disclosed rather than removed:

1. ARM M spends ~3 additional calls proposing its faults. That is the cost of knowing a
   fault at all, and no version of ARM N needs it.
2. ARM M's draws are diverse because each prompt carries a *different* fault description;
   ARM N's draws differ only by sampling noise, since `rmt.llm.ask` does not plumb
   temperature. Giving ARM N fault-driven diversity would mean giving it faults, which is
   the thing being withheld.

Neither favours ARM N, so both bias against this project's own thesis — the honest
direction for a residual to run.

## 3. Benchmark A — MigrationBench, Java 8 to Java 17

### 3.1 Toolchain

The host has `gcc`, `cargo`, `python3` and `node v24.21.0`, and no `java`, `javac`, `mvn`,
`go` or `docker`. Network reaches GitHub, PyPI and HuggingFace.

A dedicated conda environment supplies the missing half. Verified available in
conda-forge, no sudo required:

| package | versions confirmed |
|---|---|
| `openjdk` 8 | 8.0.412, 8.0.472 |
| `openjdk` 17 | 17.0.17, 17.0.18 |
| `maven` | 3.9.13 – 3.9.16 |

Two JDKs must coexist, selected per invocation by `JAVA_HOME`, because the experiment
needs P0 built under 8 and every candidate built under 17. The adapter owns that switch;
nothing else in the codebase learns about it.

### 3.2 Task pool

`AmazonScience/migration-bench-java-selected` ships metadata only — one `test.csv` of 300
rows (`repo`, `base_commit`, `num_java_files`, `num_loc`, `num_pom_xml`,
`num_src_test_java_files`, `num_test_cases`, `license`) — so, exactly like PyMigBench,
every repository must be materialised from GitHub before it can be run.

Measured over those 300 rows:

* median 7,352 LOC;
* **92 repositories have at least 5 test cases across at least 2 test files.**

Those 92 are the pool, and the `num_test_cases` column is why this benchmark was chosen
first: it is the only one here that supplies **Baseline A for free**. `-full` (5,102 rows)
is the fallback if the pool proves thinner than expected after phase 0.

### 3.3 Phase 0 ladder

Mirroring `pmb/phase0.py`, because the same thing will go wrong here:

```
clone @ base_commit -> build under JDK 8 -> run developer suite -> record status
```

with levels `cloned` / `builds_8` / `suite_runs` / `suite_green`. Only `suite_green`
repositories become tasks. This is the single largest risk in the plan and §10 treats it
as such.

### 3.4 Candidate construction

**GOOD.** G1 is the anchor: a minimal-diff migration — raise `maven.compiler.release`,
repair what breaks — admitted only on three independent checks: builds under 17, full
developer suite green, and agreement with P0 on a differential probe. G2..Gn are LLM
migrations at varied model and temperature, admitted on the same three checks. Diversity
across models is deliberate, following the brief's §8 step 3 and the same reasoning
`pmb/migbaseline.py` records: a single strong model yields a candidate population without
enough spread to contain both correct and incorrect work.

**BAD, from two independent arms.** Reporting them separately is a requirement, not a
presentation choice — see §5. Arm N is primary and Arm S diagnostic, for the measured
reasons in §5's "Which BAD population is primary".

*Arm S (seeded).* A fault-injection role — separate model instance, separate prompt,
never shown any generated test — takes a verified-GOOD migration and injects one fault
from the brief's §16 taxonomy, aimed at genuine Java 8→17 hazards:

| hazard | fault category (§16) |
|---|---|
| charset defaults (`Files.readAllLines`, `String.getBytes`) | encoding difference |
| `Locale` in `String.format` / `toUpperCase` | configuration-induced behaviour change |
| `SimpleDateFormat` → `DateTimeFormatter` semantics | incorrect time/unit conversion |
| `HashMap` / `Collectors.toMap` iteration order | ordering difference |
| `Integer` cache identity (`==` vs `equals`) | incorrect condition |
| `Math.round` on negative values, `Double.toString` precision | numeric precision change |
| removed-API substitutions with different null or exception behaviour | null-handling / exception-semantics change |
| partially migrated call sites | partial migration |

*Arm N (harvested).* Real LLM migration attempts that compile but fail the hidden oracle.
This is the natural population and it bears no family resemblance to a mutation operator,
which is precisely its value.

### 3.5 The admission filter, and the two ways it could be rigged

A BAD candidate is admitted only if it **compiles under JDK 17** *and* **the hidden oracle
confirms it actually behaves differently from P0**.

The second condition removes equivalent mutants. An equivalent mutant is unkillable by
anyone, and leaving them in silently depresses every arm's rejection rate while looking
like a fair difficulty increase.

The filter explicitly does **not** include "the developer suite still passes". That would
force Baseline A to zero by construction and make the headline comparison meaningless.
`existing_tests_pass` is instead a recorded column, exactly as the brief's §19 table
requires, and Baseline A scores whatever it honestly scores.

### 3.6 What the hidden oracle actually is here, and what it costs Baseline A

The brief's §8 step 5 wants an independent oracle. For a whole Maven repository there is
no free one, so the oracle is two instruments of unequal strength:

* **The developer suite, scored the arXiv:2504.13272 way** — not "the suite is green" but
  "every test that passed on P0 still passes on the candidate". This needs the suite only
  to *run*, so a repository with a partly-red suite still says something precise about
  which cases regressed. This is the same criterion `pmb/validate.py` already uses.
* **A differential probe**, where the repository has a reachable entry point: drive P0 and
  the candidate on the same generated inputs under the same JDK and compare observations —
  return values, thrown exception types and messages, stdout, and any files written. Per
  the brief's §11, expected values come from *executing P0*, never from asking a model.
  Probes are written once per task against P0 alone, before candidates exist, and are
  covered by the §7 freeze.

The probe is best-effort: a library without a usable entry point gets the developer suite
only, and `metadata.json` records which instruments labelled each candidate so a weakly
labelled task can be excluded from a sensitivity analysis later.

**The bias this creates, stated plainly.** GOOD admission requires the developer suite to
pass (§3.4), so Baseline A cannot false-reject a GOOD candidate: **its GAR is 1.0 by
construction, and must be reported as such rather than as a measurement.** Baseline A's
BRR remains honest — nothing about BAD admission involves the developer suite (§3.5) — and
BRR is the column Baseline A exists to supply. Any GAR comparison is therefore between
ARM M, ARM N and ARM C only.

## 4. Benchmark B — RefactorBench-JS

### 4.1 Why this one is cheap

`Create-Inc/refactor-bench` ships the hidden oracle already built and already held out.
123 fixtures, each laid out as:

```
refactoring/data/<fixture>/
    eval.config.json                # name, description, appType (web|mobile)
    refactoring_eval.config.json    # targetFile (rel. to src/), testFile (rel. to fixture)
    src/                            # the agent's input
    <name>.test.jsx                 # the holdout suite  <-- the hidden oracle
```

The benchmark's own `HARNESS_INTERFACE.md` states that agents receive the source tree and
target-file task "but not the holdout test implementation". That is the brief's §8 step 5
and §15 leakage control, pre-built and independently authored. P0 is `src/`; M is
"decompose `targetFile` into smaller modules while preserving observable behaviour".

### 4.2 Toolchain

Dependencies measured across all 123 holdout suites: `vitest` (124 imports),
`@testing-library/react` (102), `react` (28), `react-native` (4),
`@testing-library/react-native` (2); `@/` is aliased to `src/`. Test bodies use
`describe` / `test` / `it` / `expect` / `vi` / `beforeEach`.

The repository ships **no `package.json`** — "evaluators bring their own package
installation and test execution machinery" — so the runner is genuine new work: one shared
vitest + jsdom + `@testing-library/react` install with a `@/` alias, reused by every
fixture rather than installed per fixture.

### 4.3 Corpus

Classifying the 123 fixtures by what their holdout suite imports:

| class | n | pilot |
|---|---:|---|
| pure logic (no DOM, no React) | **18** | yes |
| React web | 74 | scale-up |
| React Native | 31 | excluded |

The 18 pure-logic fixtures are the pilot corpus — deterministic, no DOM, 58–353 lines of
holdout tests each: `ai_code_mode`, `ai_command_processor`, `ai_system_prompt`,
`app_constants`, `basic_web_with_auth`, `bfs_tree_traversal`, `binary_search`, `dfs_graph`,
`dijkstra_shortest_path`, `fibonacci_dp`, `insurance_reports_api`, `merge_sort`,
`n_queens`, `rule_generator`, `seo_content_data`, `seo_keywords_data`,
`seo_platforms_data`, `wallet_api`. React Native is excluded because its toolchain cost
buys no additional scientific claim.

GOOD candidates are refactorings that pass the holdout suite; BAD are (N) refactorings
that run but fail it, and (S) seeded faults confirmed by it.

### 4.4 SUPERSEDED — the oracle is the whole developer suite

> **Decision, 2026-09-15 (user-directed).** The developer test suite is **the oracle**, used
> whole and unsplit. It labels every candidate GOOD or BAD, and the experiment is then the
> comparison of ARM M against ARM N **on those labelled implementations**.
>
> Baseline A is consequently **the oracle itself**: its GAR and its BRR are both 1.0 by
> construction. It is reported as definitional and excluded from every comparison, rather
> than engineered around. This supersedes the split described below, on both benchmarks.
>
> What this gains: the full suite is a strictly stronger labeller than half of it, and the
> §3.6 asymmetry — where Baseline A's GAR was definitional but its BRR was claimed honest —
> disappears, because both are now acknowledged as definitional rather than one being
> quietly wrong. On MigrationBench the developer suite both labels and is Baseline A, which
> made that claim false there; this resolves it.
>
> What this costs: the §14 "combined" baseline and the RQ2 column lose their independent
> Baseline A. `combined_tests_pass` is retained but is `None` throughout, since combining an
> arm with the oracle that defined the labels answers nothing.
>
> The splitting machinery (`js_split.py`, and the verification in `js_oracle.py`) is kept —
> it is correct, tested, and the verification pass is still what proves a fixture's holdout
> is green on P0 before anything is scored against it — but the split halves are no longer
> used to manufacture an independent Baseline A.

#### The superseded design, retained for the record

Here Baseline A and the hidden oracle would be the same file, so Baseline A would score a
rejection rate of 1.0 by construction and the Baseline A column would be a tautology. The
suite must therefore be split: one half becomes "existing developer tests" for ARM A, the
other stays sealed as the hidden oracle. Neither half is ever shown to ARM M or ARM N.

**The split is by leaf `test`/`it` case, not by `describe` block.** An earlier draft of
this design proposed splitting on top-level `describe` blocks; measuring the pilot corpus
refuted it. Of the 18 pure-logic fixtures, **16 have exactly one top-level `describe`**
(only `wallet_api` has 2 and `basic_web_with_auth` has 5), so a `describe` split would
leave 16 of 18 fixtures unsplittable. The real structure is one outer `describe`, nested
`describe`s per function under it, and 5–24 leaf `test` cases at the bottom — so the leaf
cases are the only granularity that exists in quantity.

**Mechanism: skip-masking, not text extraction.** Both halves are the original file with
the other half's leaf calls rewritten `test(` → `test.skip(` (likewise `it(` → `it.skip(`).
Nothing is cut out, so every enclosing `describe`, every import, every `beforeEach` and
every shared fixture constant — `const sortedArray = [...]` in the outer describe body, and
its equivalents — survives intact in both halves. A text-extraction split would have to
re-derive that shared setup and would silently break wherever it guessed wrong.

Assignment is deterministic: leaf cases in source order, alternating, with the starting
parity seeded by a hash of the fixture name, so the split is reproducible and neither half
is systematically the earlier or simpler tests. The per-case assignment is recorded in
`metadata.json`.

**The split is verified, not assumed.** After splitting, both halves run against the
unmodified P0 and the harness asserts three properties: every case in either half passes;
the union of the two halves' reported case names equals the original suite's case names;
and the intersection is empty. A fixture failing any of the three is excluded from ARM A
scoring — marked `n/a`, never zero — rather than silently contributing a corrupt baseline.

## 5. Metrics, and the trap in "mutation tests beat naive tests"

An arm can win on rejection rate simply by being trigger-happy. The existing `expA`
numbers show exactly this shape — recall 50% looks respectable until precision 23% is read
beside it. So the rejection rate is never reported alone.

Primary, all from the brief's §12:

* **GAR** — good acceptance rate, correct migrations accepted / all correct migrations.
* **BRR** — bad rejection rate, the fault-detection number.
* **AP** — acceptance precision: when the pipeline says a migration is safe, how often is
  it actually correct.
* **The headline claim is BRR at matched GAR.** An arm that rejects more BADs while also
  rejecting more GOODs has not won anything. On Benchmark A this comparison excludes
  Baseline A, whose GAR is 1.0 by construction (§3.6).

Also required:

* Per-fault-class BRR (§16 table). This is where a mutation-guided arm should visibly win
  or lose, and it is more informative than any aggregate.
* **Behavioural rejections separated from structural ones**, exactly as `pmb/validate.py`
  already does. A test that dies on an `ImportError` or a missing symbol is evidence that
  the candidate is shaped differently, not that it behaves differently. The 2026-09-08
  analysis found this distinction moved recall from 0.74 to 0.23; it is not optional.
* **Arm S and Arm N reported separately, never pooled.** If ARM M beats ARM N on seeded
  faults but not on harvested ones, *that is the finding* — it would say the advantage is
  an artifact of mutation-family resemblance. Pooling would hide the single most important
  thing these benchmarks can tell us.
* **Combined (existing + generated).** A team already has a test suite, so the question
  that decides adoption is not "do generated tests catch bad migrations?" but "do they
  catch ones the developer tests miss?" `combined_tests_pass` is `existing accepts AND
  this arm accepts`, costing no extra execution since every arm already runs against every
  candidate. It is `None` where Baseline A is unavailable, and `None` on the Baseline A row
  itself, which *is* the baseline. This is the column that answers RQ2; without it we can
  say a generated arm beats developer tests 84 to 46 but not whether the 84 subsumes the 46.
* False rejection rate, accuracy, balanced accuracy, precision, recall, F1 (§12).

### Which BAD population is primary

**Arm N is the primary BAD population; Arm S is secondary and diagnostic.** This reverses
the original framing, on pilot evidence measured during implementation:

| subject scale | seeded faults (Arm S) | consequence |
|---|---|---|
| 47–139 LOC algorithmic fixtures | real faults, but the naive arm catches **15/15 (100%)** | no headroom — a strong model writes 30–50 exact-value assertions for a small total function, which is near-exhaustive characterisation, after which every fault is caught regardless of provenance |
| 1000–1600 LOC React fixtures | **11 of 12 were equivalent mutants** the oracle could not see | seeding at this scale mostly misses the behaviour the tests observe, so it yields ~8% usable faults per attempt |

So seeding works where it cannot discriminate, and mostly misfires where it could. A real
transformation attempt, by contrast, touches the code the tests exercise, so its failures
are reachable by construction — which is what Arm N collects. Arm S is retained because it
is the only population with a controlled per-fault-category label (§16), but it is reported
as a diagnostic arm and never as the headline population, and a task whose Arm S yield is
zero is not treated as a failure.

## 6. Code layout

```
additional_datasets/
    spec.py        Task/Candidate dataclasses + metadata.json schema (brief §9 fields)
    benchmarks/    one module per benchmark: refactorbench_js.py, migrationbench_java.py
                   (each owns its task construction and candidate generation)
    runner.py      the protocol: freeze+hash tests -> run every arm x every candidate
    score.py       GAR/BRR/AP, confusion matrices, per-fault-class table
    seed.py        Arm S fault injector (taxonomy-driven, isolated model role)
    harvest.py     Arm N candidate generation + hidden-oracle labelling
    arms/
        mutation.py    ARM M: mutate P0, write a test, executed kill gate
        naive.py       ARM N: P0 + M -> tests, no mutant
        ceiling.py     ARM C: sees the GOOD->BAD diff
    adapters/
        java_mvn.py    clone / build under 8 or 17 / run suite / probe
        js_vitest.py   stage fixture / install once / run suite / probe
run_additional_datasets.py    entrypoint, mirroring run.py and run_pmb.py
```

The adapters are the only language-specific code; `runner.py` and `score.py` are shared,
so a third benchmark is one adapter and one registry entry. `rmt/llm.py` is reused
wholesale — disk cache, cost ledger, concurrency cap — rather than forked.

On-disk layout follows the brief's §19 verbatim:

```
results/additional_datasets/<run>/<benchmark>/<task_id>/
    original/            P0: a pointer + commit, not a copy
    candidates/
        good_01/ ... bad_01/ ...
    generated_tests/
        mutation/ naive/ ceiling/
    hidden_oracle/
    metadata.json
```

The `<run>` segment namespaces a run the way `results/<run>/<project>/` already does in
`rmt/` and `pmb/`, so two pilots do not overwrite each other.

`metadata.json` carries every field the brief's §9 lists — `task_id`, `repository`,
`source_commit`, `transformation`, `language`, `LLM`, `model_version`,
`generation_parameters`, `candidate_commit`, `build_status`, `ground_truth_label`,
`hidden_oracle_failure`, `fault_category` — plus the suite hashes from §7.

The evaluation table emits the brief's §19 columns: `task_id`, `candidate_id`,
`ground_truth`, `compiles`, `existing_tests_pass`, `generated_tests_pass`,
`combined_tests_pass`, `number_generated_tests`, `tests_failed`, `fault_category`,
`execution_time` — with `arm` and `bad_arm` (S or N) added, since this design scores four
arms over two BAD populations.

## 7. Leakage control, enforced mechanically

The brief's §15 is the difference between measuring pre-migration test generation and
accidentally measuring fault localisation. Convention is not enough, so:

1. `runner.py` generates every arm's suite **before any candidate directory exists on
   disk**, writes each suite's SHA-256 into `metadata.json`, and refuses to score if a
   suite's hash changes afterwards. The freeze is the artifact, not a promise.
2. A harness test asserts that no candidate source text, no ground-truth label and no
   hidden-oracle test text appears in any ARM M or ARM N prompt.
3. ARM C is exempt by definition — it is *given* the diff — and is therefore reported as a
   ceiling and never as a technique.
4. **`seed.py` must not share a prompt or a taxonomy with `rmt/stage1_mutate.py`.** If the
   fault injector draws from the same list the mutation arm proposes from, the circularity
   criticism the 2026-09-08 write-up already raised lands on this benchmark too. The §3.4
   taxonomy is migration-hazard-specific and separate for exactly this reason.

## 8. Pilot

3 Java tasks and 3 JS fixtures, each with 3 GOOD and 3 BAD = 36 candidates scored by 4
arms. Order:

1. **Toolchain smoke, before any LLM call.** One Maven repository built green under JDK 8
   *and* under JDK 17; one JS fixture's holdout suite run green under the shared vitest
   install. If either fails, nothing downstream is meaningful.
2. Phase 0 ladder over a slice of the 92-repo pool, to size the real task pool.
3. The full protocol on the pilot tasks, producing the §19 table and the §5 metrics.

Budget: well under $20 in LLM spend. The same commands scale to the brief's §9 target of
20 tasks x (5 good + 5 bad) with a `--tasks` flag; nothing in the pilot is throwaway.

## 9. What success and failure both look like

This design is built so that a negative result is still a result.

* **ARM M > ARM N on BRR at matched GAR, on both Arm S and Arm N BADs.** The claim holds
  and generalises past C↔Rust.
* **ARM M > ARM N on seeded BADs only.** The advantage is mutation-family resemblance.
  This is the outcome the 2026-09-08 numbers predict, and detecting it is the main reason
  Arm N exists.
* **ARM M ≈ ARM N.** Mutation pressure buys nothing once the translation step is removed —
  which would reframe the C↔Rust result as being about translation, not about mutants.
* **Both far below ARM C.** The faults are reachable and both generators are leaving
  detection on the table; the per-fault-class table says which classes.

## 10. Risks

| risk | severity | mitigation |
|---|---|---|
| **Java build cost.** 92 repos, median 7.3k LOC, no Docker, no warm Maven cache. A real fraction will not build, and `mvn test` on `anba/es6draft` (205k LOC) is not a pilot-sized operation. | high | phase 0 ladder absorbs it; cap pilot task LOC; expect the usable pool well under 92; `-full` is the fallback |
| Equivalent mutants inflate apparent difficulty | medium | hidden-oracle confirmation is an admission condition (§3.5) |
| Arm S resembles the mutation arm's own operators | medium | separate prompt, separate taxonomy, separate model role (§7.4); Arm N reported separately (§5) |
| RefactorBench-JS Baseline A is degenerate | medium | deterministic leaf-case skip-mask split, verified against P0 (§4.4) |
| Vitest + jsdom + React Testing Library setup is fiddly | medium | pilot on the 18 pure-logic fixtures, which need none of it |
| Hidden-oracle labels are themselves noisy | medium | precedent: `results/gt_diag_fixed` showed GT bugs capped recall on RBench; record `hidden_oracle_failure` per candidate so labels stay auditable |

## 11. Out of scope

* **Baseline C** (EvoSuite or similar generic generator) — worth adding once the four arms
  are running; not a pilot dependency.
* **Defects4J** — the brief's §7 rules it out of the main experiment because its P0 is
  intentionally buggy, violating the trusted-P0 assumption. Optional secondary baseline only.
* **SWE-Refactor and RefactorBench (Python/Java)** — deferred; the adapter seam in §6 is
  what makes them cheap to add later.
* **React Native fixtures** (31) — toolchain cost without an additional claim.
* Any change to the existing `rmt/` or `pmb/` packages beyond importing `rmt/llm.py`.
